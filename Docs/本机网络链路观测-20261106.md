# 本机网络链路观测（2026-11-06）

状态：**已实现、已在当前电脑运行，真实采样与浏览器交互验证通过。** 独立入口 `http://127.0.0.1:18766/`。本次没有部署/替换线上文件、修改防火墙、重启业务服务或写业务数据库；源站仅运行本轮内存中的只读 Ping 采集进程。

## 目标、基线与实现

用户要求可视化本机、中转、源站的网络延迟与丢包。基线为后台 `Add-Phone-Support` 分支，开始时 `git status --short` 为空；之前的其他任务改动已经由其它工作提交。新增独立 `Tools/network-monitor/`，不修改 MVC 站点或原性能看板。

已读三端影响图、影响记录模板、现有 `MTH-Server/tools/perf-monitor/open-dashboard.ps1`/页面、当前网络配置及架构核对记录。复用既有源站 SSH 别名 `mth-server`，本机绑定新端口 18766。

本轮以 Builder 实现内部诊断工具。Sites 托管运行时不能执行原始 TCP/ICMP，且云端测量不能代表用户本机，所以采用本地网页与本机采集器，没有创建无实际探测能力的云站点。

调用链：Windows ICMP API / 本机 HTTP HEAD / SSH 内存脚本 → `Monitor.record` → 本地 SQLite → 只读 JSON/CSV → Canvas 曲线与失败时间带。程序不依赖第三方 Python/JS 库。

路径与指标口径见 [使用说明](../Tools/network-monitor/README.md)。源站外部 Ping 无响应，第二段明确为“源站 → 中转”的反向 Ping；两段为往返而非单向延迟，不相加。HTTP 成功响应耗时与请求失败率单独显示，不当作网络包丢失率。缺数据、SSH 错误和探测失败分开记录。

## 现场发现与未覆盖

- 本机存在 Mihomo TUN 默认路由，单纯 TCP connect 曾显示 0.3–0.6 ms，不能作为真实服务器 RTT。工具用真实 ICMP 和收到完整 HTTP 响应头后的耗时，不修改代理配置。
- 同时段源站本机访问 `127.0.0.1:8080/` 的 HEAD/GET 为 200；本机经中转返回 504、直连出现空响应，说明需要结合实际路径进一步排查。没有用本轮事实断言全体玩家不可用，也没有顺手改变线上配置。中转 SSH 曾在 banner 阶段被断开，未取得进一步现场配置。
- 测量来自当前电脑与源站，不代表手机 Wi-Fi/移动网络。没有测试玩家登录、下注、每款游戏的实际游戏协议延迟。
- 未安装开机启动；当前电脑停机/休眠/停止采集后留空。源站无持久探测服务；窗口最多 24 小时，SQLite 保留 7 天。
- ICMP 未回包可能包含过滤、限速与链路丢失；HTTP 失败包含超时、连接问题或服务器错误。任一指标都不直接等同于游戏数据包丢失。
