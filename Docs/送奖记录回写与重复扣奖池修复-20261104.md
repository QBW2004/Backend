# 送奖记录回写、重复扣奖池与 ATT 牌型不符修复

状态：**本地修复、隔离构建及定向验证完成；未上线，未改线上资金或历史记录。**

## 问题与根因

1. 点石成金 `ServerRun::ServerCenterUpdateControlConfig` 的已入座分支遗漏 `mPrizeControlId`，其他两个接收分支已赋值。送奖次数可完成，但实际开奖报文的 `fundedControlId=0`，中心服只写中奖记录，跳过送奖回写和奖池流水。后台 1.0.103 隐藏已结束未开奖的记录后，这些记录消失。
2. 六款牌机及未开放的金皇冠同源逻辑，在次数用完后调用 `UserCtrl()`，保留旧送奖编号进入默认放水循环。后续中奖仍可能被视为人工送奖、扣旧奖池，并覆盖旧记录的实际牌型。这是 ATT 持续扣款、赠送与开出名称不符的一条路径。
3. ATT 基础牌型旧算法依赖玩家留牌，丢掉鬼牌或留牌不兼容时会放弃目标；但次数已在一手按 `type_expect` 提前消耗。补充检查在旧代码的 3,520 个组合中复现 3,142 次目标不符。
4. ATT 原开奖名称只写“满花+基础牌型”，未区分普通/正宗满花与方块彩金，无法直接与赠送选项逐项核对。

中心存储过程允许已完成的控制记录接收最后一手开奖，这是正常需求：次数消耗发生在一手，开奖发生在二手。不能简单增加 `Status=0` 限制，否则最后一手又会漏记。

## 本次变更

- 点石成金补齐在桌玩家控制编号下发。
- `Common/UserInfo.h::CaptureCardControlHit` 统一当局编号快照：只在剩余次数大于零时消耗；每手重置快照；人工标记和扣款编号只来自有效送奖编号。
- 六份 Handler（大白兔复用火凤凰，合计七个编译变体）的 `UserCtrl()` 清除旧编号；默认循环继续按原节奏运行，但不再上报旧送奖消耗、不再把自然局计为旧送奖。最后一手的编号独立保留，多次送牌和大白兔连庄仍逐手记账。
- ATT 基础 1～12 与扩展 13～25 采用同一保证出牌流程：一手组成可成立的指定牌面，二手保留该牌面，玩家留牌不会让本次送牌落空。仅 `cardAction=8` 的有效控制使用；默认循环、自然局、点杀和金拇指入口保持各自逻辑。算法存盘结构未变。
- ATT 从实际二手牌生成“普通满花·… / 正宗满花·… / 方块彩金·…”名称；金拇指继续按实际档位和金额上报。

后台查询、权限、奖池存储过程不变；无需新 SQL、WebVer 或 APK。后台仍为线上 1.0.103。
