## 本轮新增缺陷

### 1. [P1] 两款押注游戏的控制押注额被后续玩家清零

位置：`../MTH-Server/ServerBetDT/ServerRun.cpp:2285`、`ServerBetAnimal/ServerRun.cpp:2211`；影响彩金单挑、幸运六狮。

`RunResult` 在每个非庄家玩家的循环内执行 `mCtrlKillBetAll=0`。首个被控玩家已经填好控制标志、各门下注与总押注后，后面的普通玩家再次清零总押注；由于 `mCtrlKillFlag` 已非零，后者不会重新填充控制数据。即使后面的玩家根本未下注，也会触发。

抽取两套真实生产循环复现：被控玩家押注 100，随后遍历一个未下注普通玩家，控制标志仍为吃分/放水，各门下注仍为 100，**总押注却变成 0**。两种控制、两个游戏均复现。

后果：幸运六狮吃分主分支要求 `mCtrlKillBetAll != 0`，因此跳过；两款放水比较“返奖是否小于总押注”时以 0 为基准，返奖为 0 也不继续寻找盈利结果。彩金单挑吃分同样使用了错误的净收益基准。

建议：总押注的初始化移到玩家循环之前，并将目标玩家、控制标志与押注快照作为一组保留；覆盖目标玩家位于首/中/末位、后续未下注玩家、两种模式的测试。

修复成本：低；收益：高。规则：正确性、边界条件。

### 2. [P1] 彩金单挑庄家收益控制绕过玩家吃分/放水

位置：`../MTH-Server/ServerBetDT/ServerRun.cpp:2571`、`:2604`。

`ArithmeRun` 在存在庄家且 `RunBankerCtlPick()` 成功时，直接跳过 `pAlg->AlgMain()`；玩家吃分/放水的计算位于后者调用的 `AlgCheckPrize`。庄家选门没有读取玩家控制标志和目标，后台仍可显示控制执行中，实际仅按庄家收益目标选结果。

本地执行真实 `ArithmeRun`，将庄家选门边界替身设为成功，确认 `AlgMain` 调用次数为 0。线上两个内部桌号 2、3 的配置已经满足“启用庄家收益控制”条件；还需当局有有效庄家才进入此路径。本次未在这两桌制造在线牌局。

建议：明确并实现庄家收益目标与玩家控制的优先级/冲突规则；不能让后台成功受理后静默跳过玩家控制。

修复成本：中；收益：高。规则：正确性、状态与实际行为一致。

### 3. [P1] 放水耗尽奖池的最后一笔收益漏计进度

位置：`../MTH-Server/ServerCenterNew/ServerCenterRun.cpp:8088`；关联 `Database.cpp:5020`。

结算先 `SavePrizeReleaseRecord` 扣奖池，再 `StopExhaustedPrizePools` 将余额不足的 Active 控制置为失效，最后才调用 `CheckTotalControlOnSettle`。进度累计只读取 Active 记录，导致耗尽奖池的这笔结算被跳过。

执行真实中心上报/停止/进度方法，持久化边界模拟“本笔扣款后奖池耗尽”：净赢 10 钻，放水记录从 Active 变为 Expired，而 `GrantedCoins` 仍为 0。此复现验证生产调用顺序，数据库扣款由替身模拟，不是线上扣款试验。

影响非麻将的共用中心结算链；不将麻将独立事务结算混入此结论。后台“已放”与玩家实际收益、奖池账目可能不一致。

建议：本笔结算的控制归属、进度累计、目标完成和余额耗尽停止应绑定同一记录，确保先记完本笔再停止，并覆盖“同笔达目标且余额归零”。

修复成本：中；收益：高。规则：金额/进度一致性、事务边界。

### 4. [P1] 奖池耗尽的迟到通知仍可清掉新送奖

位置：`../MTH-Server/ServerCenterNew/ServerCenterRun.cpp:11384`；关联 `Database.cpp:5036`、`ServerCenterRun.cpp:4514`。

`TakeExhaustedPrizeControls` 事务内绑定 ID 关闭旧记录，但事务后只返回“账号、模式”。随后 `StopExhaustedPrizePools` 无条件执行 `ApplyTotalControlNow(id, oldMode, 0)`，没有携带旧记录 ID 或重新核对当前送奖。

在“旧送奖因奖池耗尽提交失效 → 充值并新建/下发送奖 → 旧停止通知迟到”交错下，旧 mode6 停止会把新送奖清为 `ctrlType=0`。后续 `ReapplyPendingTotalControl` 只恢复吃分/放水；在牌机/拉霸放水只累计进度的设计下，新送奖不会自动恢复。

本地用真实停止/应用/恢复方法，在 6 款开放牌机和 3 款拉霸复现：新送奖数据库仍 Active、剩余 2 次，共存放水仍 Active，但发给游戏的控制为 0。持久化及发送边界为替身，交错点可控。麻将 `UserCtrl` 会重读数据库权威快照，不归入这 9 款。

建议：停止事件保留控制 ID，按当前已提交状态刷新包括送奖在内的完整控制；重试队列也不能只存账号和模式。

修复成本：中；收益：高。规则：并发安全、迟到消息幂等。

另外，六款牌机 `ctrl26` 只判断强度是否大于 0，均采用同一内置概率套；不同强度并不对应不同概率。这是能力限制，手机默认强度 3 不受档位选择影响。
