# 手机端后台数据加载提速改造（2026-08-29）

> 对应分支 `Add-Phone-Support`。目标：提升手机端后台（/Mobile）列表与操作接口的响应速度。
> 服务端查询链路与手机端首屏渲染同时优化；操作类请求先返回受理状态，最终指令由既有发件箱补偿。

## 一、数据库补丁（必须先于代码部署执行）

`Docs/sql/性能索引.sql`（幂等，可重复执行；已同步 `docker/mysql/init/40_性能索引.sql` 并加入 `Tools/reset-db.ps1`）：

- 新增二级索引 12 个：`users(AGENCY)`、`users(INHALL)`、`userrelations(ID)`、
  `useroptlog(UserID,LID)`、`useroptlog(REC_TIME)`、`rechargerecords(CreateTime/GameID/Agency)`、
  `rechargerecords(Processed,CreateTime,GameID)`、
  `agencyoptlog(REC_TIME)`、`loginmissrecord(ID)`、`user_daily_winloss(DAY)`。
  这些表此前只有主键，玩家列表/记录查询/日志清理全部全表扫描。
- `user_daily_winloss.UserID` 由 latin1 调整为 utf8mb4，消除与 `users.ID` JOIN 的跨字符集隐式转换
  （EXPLAIN 验证 join 从无法走索引变为 PRIMARY eq_ref）。

**线上部署时**：在 MySQL57 上对 `mth` 库先执行一次该 SQL，再按正常流程发布代码。

## 二、读接口改造（BLL）

| 位置 | 原实现 | 现实现 |
|---|---|---|
| `B_Records_MySQL.Get_PlayerRecords`（中奖历史/游戏轨迹） | `UserOptLogs.AsEnumerable()` 全表拉内存 + 内存 join/分页 | join/过滤/Count/分页全部下推 SQL |
| `B_Records_MySQL.Get_AgencyRecords` | 同上（AsEnumerable） | 同上下推 |
| `B_Users.QueryUsersPaged`（离线玩家/封禁玩家/会员盈亏） | 权限范围全量 `ToList()` → 内存排序 → Skip/Take；win-most/loss-most 还对全量名单补今日输赢 | 一条 COUNT + 一条分页 SQL；`user_daily_winloss` LEFT JOIN 直接带出今日输赢；IN(agencies) 参数化下推 |
| `B_Users.GetUsersList`（玩家搜索/列表） | 非超管按代理逐个执行 SQL（N+1） | 单条 `agencies.Contains` IN 查询；分页下推；增 UserID 稳定次序 |
| `B_Users.FillCurrentPlayInfo` | 全量 `OrderBy(LID desc).ToList()` 后内存 GroupBy 取最新一条 | 按 `UserID` 取 `MAX(LID)`（走 (UserID,LID) 索引）再回表取 7 列 |
| `B_ReChargeRecords.GetReChargeRecordsForPhone` | 全表 `ToList()` 后内存求和/筛选/分页 | SUM/Count/分页均下推；玩家名只为当页行补齐 |
| `UserInfoController.GetOnlineUsers` | 可见性、盈亏和今日输赢重复查询 | 复用首次可见性批量查询结果，只保留一次最近登录补充 |

手机端玩家页先渲染在线/离线基础卡片，再异步补齐控制状态；账号搜索并发查询账号和昵称，控制状态接口不会阻塞首屏。

### 口径说明（有意保留/可忽略的差异）

- `INHALL` 过滤条件沿用 EF 生成的 `NOT (INHALL = 1)` 语义（NULL 行排除），与改造前 SQL 行为一致。
- `profit-desc/asc` 排序对 `COINS_BUY/COINS_BACK` 为 NULL 的行按 0 参与计算（列有 DEFAULT 0，实际不出现 NULL）。
- `GetReChargeRecordsForPhone` 手机入口显式传 `Processed = -1`，BLL 再固定套 `Processed = 1`，因此“全部/充值/退分”
  三种分类都只展示已经生效的流水，不会把未处理或拒绝订单混入列表和合计。
- 会员盈亏列表与统计卡使用最近 7x24 小时内的已生效充值/退分流水；今日字段仍只计算当天窗口。
- 手机端玩家充值/退分完成数据库事务后，将在线玩家的 `LK/UL` 指令写入 `gamecommandoutbox`，接口不再同步等待中心服管道；电脑端保留原同步入口，发件箱重试服务负责最终下发。

## 三、清理任务集中化

`B_Records_MySQL.CleanupExpiredRecords`（业务记录与日志表的 7 天滚动 DELETE）原来被列表接口和充值/兑换指令流
同步内联调用，读接口变全表扫描+写锁。现收敛为：

- `CleanupExpiredRecordsThrottled()`：进程内节流（默认每小时最多一次），挂到 `Global.asax` 既有 60s 定时任务。
- 原 10 处内联调用全部移除（`B_Records_MySQL`×2、`B_ReChargeRecords`×3、`B_Recharge`×3、
  `B_GameRecords`×1、`B_ManagerOpt`×1）。
- 影响应用启动后的第一个小时内可能出现 >7 天旧数据（定时器 60s 内即首轮清理，可忽略）。

## 四、其余配套

| 项 | 说明 |
|---|---|
| `Global.asax` 会话只读 | `/Game/*`、`/Mobile/*` 请求改 `SessionStateBehavior.ReadOnly`（唯一写会话的 `Game/UserInfo/Register` 例外）。同一管理员并发 AJAX 不再被会话锁串行化 |
| `PipeGameServerClient` 管道熔断 | 游戏服不可达时每次指令阻塞 5-10s；现失败后 30s 冷却期内直接快速失败（原始 QA/QU/UL 结果驱动熔断），成功即复位。踢人/锁定等指令仍由 outbox 重试补偿 |
| 手机总控操作 | 旧流程在 HTTP 请求内同步等待 UC 管道响应 | `ApplyTotalControl`/`CloseTotalControl` 的手机请求写入 `gamecommandoutbox` 后立即返回“已受理，处理中”，电脑端保持同步语义 |
| `GameDbContext` SQL 日志 | `Database.Log → Trace` 改为 appSettings `sqlTrace=1` 时才开启 |
| `B_LoginMissRecord` | 60s 定时重置任务的时间过滤下推 SQL；`SaveChangesAsync` 未 await 改同步保存（避免丢写） |
| `_MobileLayout.cshtml` | jquery-2.1.4.js → min 版（约 280KB → 82KB） |
