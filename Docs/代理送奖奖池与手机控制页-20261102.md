# 代理送奖奖池与手机控制页（2026-11-02，已实现、未发布）

已按《奖池管理.docx》调整手机页面，并按运营在聊天中最后确认的四条规则补齐资金逻辑。文档是页面需求参考，实际资金规则以本轮聊天确认内容为准。本轮没有操作线上数据库、后台或游戏进程，没有发布 APK。

## 资金规则与页面行为

- 每个后台操作账号独立持有送奖奖池，初始余额为0。充值从自己的 `admin.COINS` 转入，退回执行相反操作；钱包与奖池及流水在同一事务更新。只接受正整数钻，实际结算保留8位小数。
- 送牌下发前，用玩家所选游戏的当前实际押注（按桌台兑换比换算成钻）乘以所选牌型倍率，再乘以控牌次数，校验操作员奖池余额。例：大字版5钻 × 四梅65倍 =325钻；324拒绝、325通过。不足时弹窗原文为 **奖池余额不足，请充值奖池**。确认框显示本次核算金额；提交时重新查询押注，押注已变化则要求重新查询。
- 手机控牌固定1次、5把之内。必须查询到玩家在线、在所选游戏且已上报有效押注和兑换比；旧中心服或离线时不能猜测金额下控。牌机固定赔率来自当前控牌选项目录；随机连线、幸运灯、免费链等变动奖励显示预估备款金额，实际支出按实际开奖事件结算。
- 放水发起时余额须覆盖目标；执行中按玩家实际净收益记账。100钻奖池、目标100、实际净赠送120时记为-20，随后结束该奖池现有送奖。余额仍小于等于0时禁止新送奖，须从我的余额充值补足。吃分不扣奖池。
- 控牌按实际开奖金额扣款；放水与控牌同时生效时，重叠的同一笔收益不会重复计费。已下发到游戏的实际结算会据实入账，余额检查属于下发时校验，不是对未来押注或全部待开奖控制做冻结。
- 充值、退回只操作当前登录账号自己的奖池。GUID请求号防止同笔转账因重试重复扣款。上级查看下属流水沿用代理管理范围校验。

手机「送奖管理」包含一行账号查询、三张钻统计卡、控制类型/游戏/牌型、奖池与我的余额、应用/移除、7天默认送奖记录。记录含游戏、账号、状态、机台、送奖牌型、实际牌型、实际钻金额、时间，窄屏横向查看后半列。历史控制没有可信事件关联时，实际开奖字段留空，不把自然中奖按时间接近拼成送奖。

代理详情增加奖池余额；「代理流水」默认奖池模式，可切回原资金流水，支持全部/玩家/充值/提取、玩家账号、日期和分页，展示充值合计、负数提取合计和净送奖合计。

## 实现范围

后台新增 `B_PrizePool`、`CardPrizeQuoteRules`、`Config/card-prize-quotes.json`、`PrizePoolController`。总控申请与资金校验/控制归属元数据处于同一事务；现有单控历史不回填。新增三个InnoDB表 `agentprizepool`、`agentprizecontrol`、`agentprizeledger`，由两个存储过程处理实际控牌与放水增量。

中心服按显式ControlId接收子游戏实际开奖金额和兑换比，和中奖记录在同一事务记账；失败保留原事件号重试，事件号唯一索引防重。放水从实际结算原始增量记账，不拿整数目标进度冒充支出。余额耗尽后撤销相应控制，并重试暂未送达的停止指令。待重试队列仍在进程内存，未实现断电后完整逐笔恢复。

登录/下控/控牌消耗消息追加可选ControlId尾段，旧未资金关联报文保持原格式。相关10套游戏源码、11个工程已编译，包括大白兔共用火凤凰源码；大白兔X7～X14命中识别一并补足，否则实际控牌命中不能正确消费和计费。麻将实际小数押注追加精确尾段。

## 发布条件与验收

1. 以发布时实际线上版本隔离构建，工作区其他待发内容须逐项确认，不能直接整包覆盖。
2. 完整备份代码、运行状态及数据库（含routines/triggers），先执行 `Docs/sql/代理送奖奖池-20261102.sql`，再成套发布后台、中心服及有送牌功能的在服游戏。若此前玩家盈亏统一钻口径未发布，须一并带入其SQL、中心服及全部在服游戏的兑换比上报改动，手机今日/总盈亏才能保持真实钻单位。
3. 新增 `Config/card-prize-quotes.json` 必须随后台发布，更新WebVer高于发布时线上值。页面与服务端配套，不需要APK。
4. 存量控制不自动归属奖池或补扣历史资金；上线窗口需核查既有执行中送奖，决定结束后重新设置。新增奖池初始0，不从历史充值推算余额。
5. 在隔离验收环境用测试代理检查：钱包100/奖池0→充10→90/10→退10→100/0；5钻押注四梅在324/325边界；目标100实际120后余额-20、禁止新赠送、充值补足后恢复。代理流水核对相同时间范围的变动与余额；不要拿线上真实玩家下注验证。

随机额外奖、后续加注、并发在途控制都按实际开奖记账，不能把下发时静态报价理解成未来支付硬上限。若后续需要严格冻结所有在途控制、限制玩家后续押注或锁定随机奖励上限，应另行明确产品规则并配套实现。
