# 总控吃分/放水目标按钻累计（2026-11-02）

状态：已实现并通过本地验证，未发布。需中心服配套隔离发布；后台仅文案标注，无 SQL / 子游戏 / 客户端改动。

## 需求

运营要求送奖（放水/吃分）目标按「钻」计，不再按机台分。此前口径：中心服 `CheckTotalControlOnSettle` 用结算同步包相邻累计增量直计 `usercontrolstatus`——鱼机 ÷10、其余游戏原始机台分；`TargetCoins`/`GrantedCoins`/`ConsumedCoins` 字段名虽叫 Coins 但装的是分。100 分=1 钻 的游戏设目标 1000，实际只放约 10 钻 的量。

## 改动

### 中心服（MTH-Server，仅 `ServerCenterNew.exe`）

- `ServerCenterPlayerBetSync`：结算同步报文携带 `unitsPerCoin`（实际桌台兑换比，统一币口径已加尾段）时，本局原始增量按该比率折算成币再累计总控进度。对**增量**折算（不是累计值）：玩家换桌换率时每笔仍按各自比率入账，不串率。
- 不足 1 币的零头挂 `UserInfo::mCtrlCoinCarry` 随会话累积：盈利零头暂缓、亏损零头进位（沿用鱼机 ÷10 的「对庄家有利」口径，floor 向负无穷取整）。字段随 `mLastSyncWinLoss` 在进房/离房/登出/构造全部复位点一并清零。
- 旧版子游戏无兑换比尾段（`unitsPerCoin==0`）：维持旧口径——鱼机 ÷10、其余原始分累计，安全降级。
- `CheckTotalControlOnSettle`/`AddTotalControlProgress`/控牌(6)次数控制均不变；离场补记仍只走 `BetSync` 唯一入口，不重复累计。

### 后台（MHT-Backend，仅文案）

- 手机端「控制」页、电脑端用户管理/在线玩家两处总控窗：目标输入标签 `目标` → `目标（钻）`。
- `B_UserControl`/`UserInfoController` 注释中的「钻阈值」（币→钻改名后）语义自此名副其实，无需改动。
- 状态回显「目标 N / 已放 M / 已吃 M」数值自此与目标同为钻单位。

## 注意：存量执行中记录

切换瞬间执行中的 mode4/5 记录，已累计进度是按分记的、新增量按钻加——同一条记录口径混合。分口径下的大目标在钻增量下会进展很慢。发布时建议人工核查执行中记录，必要时重设目标；不自动改写/过期历史数据。

## 发布依赖

- 生效需中心服换版 + 各子游戏已带 `unitsPerCoin` 尾段（与「玩家盈亏统一币口径」同一趟：先 SQL，再后台+中心服+14 款在服子游戏成套隔离发布）。单发中心服时，未带尾段的旧子游戏控制进度仍按分累计（降级，不错乱）。
- 无 SQL 迁移、无子游戏协议变更、无 APK 改动；后台可随同批发，仅标注文案。

## 发布后人工验收

1. 在 100 分=1 钻 的游戏给测试号设放水目标 10，完成净赢 500 分 的一局 → 已放应增加 5（钻），不是 500。
2. 继续净赢 50 分 多局 → 进度按 0.5 钻 零头暂缓，累计到整钻才 +1。
3. 中途换不同兑换比的桌台 → 各局按各自比率折算累计，不串率。
4. 设吃分目标并产生亏损 → 已吃按钻进位（-1.5 钻 记 2）。
5. 旧版未带尾段子游戏（若有）下结算 → 进度仍按原口径累计，无报错。
