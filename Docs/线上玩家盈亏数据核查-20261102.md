# 线上玩家今日与总盈亏核查（2026-11-02）

核查时间：2026-11-02 18:41～18:50（UTC+8）。线上后台版本 **1.0.95**，`IsRMB=0`，金额不会在前端再除以 `ExchangeRate=100`。Windows、MySQL 会话及全局时区均为 UTC+8，今日日期为 2026-11-02。

**结论：不能认为当前今日/总盈亏正确。已证实三项问题：机台分与币混用、离场自动收奖漏计、电脑端首屏总盈亏显示为 0。** 手机列表、会员盈亏及详情页读取日累计表的过程基本一致，但源表本身存在金额口径问题。

本次仅核查接口、配置、现有结算记录及代码，没有部署、重启、下注或修改线上业务数据。远程只读采集工具放在 `C:\Temp\winloss-audit-20261102.ps1`，本地原始结果保存在 `.build/`；查询凭据只在进程内使用，结果不含密码。

## 1. 已证实：多款游戏以机台分直接累计，却按币显示

手机玩家卡片明确标注“今日输赢(币) / 总输赢(币)”。但中心服 `ToDailyWinLoss` 只对鱼机作固定缩放，其余游戏直接返回原始 `mTotalWinLoss`；这些游戏的输赢是机台分。

本次读取的线上桌台配置中，火凤凰(5)、大字版(15)、明星97(16)、ATT满花版(25)、点石成金(37)、水果拉霸(40)、NBA(44)、水浒传(53)、大白兔(55)的样本桌均为 **100 机台分 = 1 币**。押注游戏与麻将等又存在 1:1 桌台，故不能把全表统一除以 100。

可独立复核的线上例子：

| 项目 | 15002，大白兔，2026-11-02 15:25:16～15:26:52 |
|---|---:|
| 进入余额 | 231 币 |
| 离开余额 | 2,594 币 |
| 净增加 | **2,363 币** |
| 进入、离开余分 | 均为 40，差额为 0 |
| `useroptlog` 离桌 `SCORE` | **236,300 机台分** |
| 当日累计采用的口径 | 原始机台分，未按该桌 100:1 折币 |

证据：`useroptlog.LID=3132/3133`；`userscoresnapshotledger.LoginSession=124`，首末快照 `LID=18500/18510`；`roomtableconfig GAME_ID=55, TableIndex=0, OneCoinScore=100`。

源码位置：

- `MTH-Server/ServerCenterNew/ServerCenterRun.cpp:129`：`ToDailyWinLoss`。
- 同文件 `:5748`：定时将累计值换算后求差。
- `MTH-Server/ServerCenterNew/Database.cpp:2249`：增量累计到当日 `WINLOSS`。
- `TTY.Web/Scripts/app/phone/phone.players.js:160` 附近：输赢标签使用“币”，值直接交给 `M.gold`；线上 `IsRMB=0` 时无额外换算。

影响：今日盈亏和由每日记录求和的总盈亏都受影响，多游戏合计还会混合不同单位。当前日合计 **760,166**、总合计 **1,067,765** 只能视为现有累计表的数值，不能作为已核准的币盈亏。

修复方向：在游戏结算源头按结算当时的实际桌台兑换比统一币口径，并保留所需小数精度；历史重算须按游戏、桌台、会话及当时兑换比处理，不能直接对 `user_daily_winloss` 整表除以 100。

## 2. 已证实：离场自动收奖后，余额与盈亏上报存在差额

同一玩家的下一场大白兔：

| 项目 | 15002，2026-11-02 15:27:07～15:28:42 |
|---|---:|
| 进入余额 | 2,594 币 |
| 离开余额 | 4,920 币 |
| 实际净增加 | **2,326 币** |
| 进入、离开余分 | 均为 40 |
| 离桌上报 `SCORE` | 216,600 机台分，即 **2,166 币** |
| 少计 | **160 币（16,000 机台分）** |

证据：`useroptlog.LID=3134/3135`；快照 `LoginSession=125`、首末 `LID=18511/18524`。最后两条快照在 15:28:39～15:28:42 从 4,760 变为 4,920 币，盈亏上报未包含这笔差额。当天该账号操作记录无充值/退币事件。

源码与该现象吻合：`MTH-Server/ServerCardPhenix/ServerHandler.cpp:271` 的 `FinishAlgRound()` 会在离场时完成牌局并调用 `WinScore(&mGameScore)`，大白兔分支还会收活动奖，但没有将这次分数变化加入 `mTotalWinLoss`，也没有补发 `SendBetSyncToCenter`。`SaveUserInfo():300` 会保存收奖后的余额，造成“余额已经增加、盈亏还是收奖前的值”。大白兔复用该源码编译。

影响：即使修正 100:1 单位，遗漏的收益仍然存在。其他复用离场收尾逻辑的牌机需要一起核查。

修复方向：离场完成整条收奖流程后，按最终净收益统一补记并同步，避免重复记账；同时覆盖主动离场、断线、被踢及半局退出。

## 3. 已证实：电脑端“用户管理”首屏总盈亏全部为空

实调 `/Game/UserInfo/GetUsers`：35 个玩家的 `Profit` **全部为 null**；页面 `fmtWinLoss` 使用 `Number(value || 0)`，会显示为 0，其中 **20 个玩家实际累计表总盈亏非 0**。

例：15002 首屏总盈亏为 0，而同刻日累计表与详情接口返回 654,697；test01 首屏为 0，详情返回 474,368。这里的“详情返回”仍是第 1、2 项问题下的旧口径数值。

根因：`YYT.BLL/EF/B_Users.cs:497` 的 `GetUsersList` 只调用 `FillCurrentPlayInfo` / `FillTodayWinLoss`，漏掉 `FillTotalWinLoss`。控制器注释称总盈亏已经填充，但实际没有。

随后页面每 3 秒调用 `/Game/UserInfo/GetVisibleUserRows`，该路径会调用 `FillTotalWinLoss`。本次实调该刷新接口的 35 行，与累计表全部一致。因此表现为首次打开/重新查询时总盈亏为 0，等待刷新后才补上。

修复方向：首屏分页查询也补齐累计游戏输赢，保持与刷新接口相同的口径。

日累计表共78行，日期从2026-10-17到11-02；无重复 `(UserID,DAY)`，无已不存在玩家的孤立累计记录。总累计合计与会员统计接口同为1,067,765。没有发现本轮统计把充值减退币当成游戏盈亏。

核查时中心服返回在线玩家0人，因此未进行真实在玩玩家连续变化或跨零点实测。本次接口采集单轮约2.3秒，结算/快照采集约2.3～3.4秒；无需运营在线下注才能确认上述问题。

另有源码风险：中心服定时累计和离场补差都跳过 `mTotalWinLoss==0` 的场景。若会话曾有非零盈亏已落库，后来回到恰好0再离场，旧的已落库增量可能未被冲回。该风险由源码可直接推出，本次没有把任何历史差额武断归因于此，修复时应覆盖“亏损→回本→离场”。

历史完整修正尚不能仅靠现有日累计表完成：该表没有游戏、桌台和结算事件明细，操作日志还有滚动保留限制；跨天会话也不能简单按离桌日期汇总替代实时日增量。应先修新结算口径，再在隔离副本上逐会话核算可恢复的历史范围。
